# 메타 인덱싱 / 검토 문서 편입 방향 (초안)

> 작성일: 2026-07-23
> 상태: 브레인스토밍 — 다음 세션에서 구체화 예정
> 계기: dfas_discovery 프로젝트(agent+collector, 2개월/4만 줄/122커밋 규모)를 진행하면서
> 기존 LOADSTAR 구조(WP/DWP 중심)만으로 관리가 어려운 지점을 실제로 겪음

## 1. 문제의식

프로젝트 규모가 커지면서 WP(WayPoint)/DWP(Data WayPoint) 단위로 딱 떨어지지 않는 문서들이
계속 생겨났다:

- 프로젝트 중간 점검 메모, 미구현 항목 브레인덤프(TODO 리스트류)
- 특정 주제에 대한 리서치/검토 메모(예: OpenSearch 도입 검토 — EAV 패턴, analyzer 설계,
  RDBMS 이원화 등 여러 WP를 가로지르는 내용)

이런 문서의 특징:
- **WP보다 범위가 넓다** — 여러 WP/주제를 가로지르는 요약·정리 성격.
- **포맷을 정형화하기 어렵다** — 억지로 스키마를 강제하면 결국 안 지켜짐.
- **현재 구조엔 이들을 걸어둘 자리가 없다** — Map은 `IDENTITY`/`WAYPOINTS`/`COMMENT`뿐이라
  WP보다 넓은 범위의 문서를 참조할 REFERENCE/ATTACHMENTS 슬롯이 없음(WP엔 있음 —
  예: `proc_livesystem.md`의 `ATTACHMENTS: file:///...`). 결과적으로 이런 문서들은 프로젝트
  디렉토리 어딘가에 방치되고, AI가 Map→WayPoint 지연 로딩 탐색을 해도 존재 자체를 알 수
  없다.
- 부수적으로, 파일이 여러 디렉토리에 흩어지면서 **경로를 매번 사람이 AI에게 직접 알려줘야
  하는 번거로움**도 누적됨.

## 2. 논의 결론

### 2.1 문서 자체 포맷은 강제하지 않는다
자유 서식 유지. 대신 **문서를 가리키는 인덱스 쪽에만 최소 구조를 둔다.**

### 2.2 Map과 유사한 "지도" 역할의 인덱스 + 메타 태그
- 각 문서에 성격 메타(예: DB / 처리흐름 / 향후검토 등, 다중 태그 허용) 부여.
- **물리적으로 여러 "뷰" 파일(시간순 뷰, 카테고리별 뷰 ...)을 만들지 않는다** — 인덱스 파일
  하나에 구조화 필드(제목/경로/날짜/태그/한줄요약)만 넣고, 정렬·필터링은 읽는 시점에
  AI 또는 뷰어가 처리. 뷰를 파일로 물리화하면 문서 추가마다 전부 갱신해야 해서 유지보수
  부담이 커짐.
- 참고 사례: Claude의 자체 메모리 시스템(`MEMORY.md` 인덱스 + 개별 파일 frontmatter의
  `type:` 태그) — 최소 구조 인덱스 + 자유 서식 본문 조합이 실제로 잘 작동하는 선례.

### 2.3 더 큰 통찰 — WP/DWP 자체도 같은 방향 검토 가능
OpenSearch EAV 패턴 논의(고정된 소수의 "값 슬롯" + 자유로운 필드명 조합으로, 해석기만
추가하면 이질적 구조의 데이터를 계속 편입시킬 수 있었던 설계)에서 착안 — WP/DWP의 현재
고정 섹션(`CODE_MAP`/`TODO`/`ISSUE`/`COMMENT` 등) 대신, **포맷은 느슨하게 풀고 메타를
강화하는 방향**도 장기적으로 검토 대상. (아직 구체화 전 — §4 참고)

### 2.4 파일 기반(서버 불필요) 검색 툴 조사
| 툴 | 특징 |
|---|---|
| **SQLite FTS5** | 가장 실용적 후보. 이미 dfas_agent가 SQLite를 여기저기 사용 중이라 새 의존성 부담 적음. 단일 파일, 전문검색(BM25)+일반 컬럼 결합 가능. |
| Tantivy(Rust) | Lucene급 진짜 검색엔진 아키텍처, 서버 없이 라이브러리로 사용(Quickwit/Zulip 검색이 채택). |
| Bleve(Go) / Xapian(C++) / Lucene 자체 | 같은 카테고리 — ES/OpenSearch는 Lucene을 서버로 감싼 것뿐, 서버 레이어 없이 라이브러리로 직접 사용 가능. |
| DuckDB | 검색보다 "구조화 메타의 다면적 조회(시간순/카테고리별 집계)"에 강점. FTS 확장도 있음. |

→ **SQLite FTS5를 1차 검토 대상으로 결정.**

### 2.5 핵심 아키텍처 결정 — "파일이 원본, DB는 파생 검색 인덱스"
DB를 원본 저장소로 완전히 옮기는 안은 기각(트레이드오프가 큼):
- git diff/blame으로 "이 WayPoint가 언제 어떻게 바뀌었는지" 추적 불가(바이너리 DB).
- `loadstar edit`/직접 md 편집(MASTER_GUIDE §5.1 GUIDELINE-1)의 단순함 상실.
- 사람이 ripgrep/IDE 검색으로 그냥 훑는 것도 불가.

**대신**: md 파일 = 여전히 진실의 원천(그대로 유지) / SQLite FTS5 = **메타정보 + 역색인만**
담은 파생 검색 레이어 — 필요하면 파일에서 재색인해서 다시 만들 수 있는 캐시 성격. "데이터는
단순하게 관리(파일), 조회 방법은 다양화(인덱스+쿼리)"라는 원칙으로 수렴 — 같은 세션에서
별도로 논의한 OpenSearch 재설계 방향(RDBMS=원본, OpenSearch=좁은 범위 검색, 통계=RDBMS
롤업)과 동일한 패턴이 LOADSTAR 자체 구조에도 반복 적용됨.

## 3. 결정된 것 vs 아직 아닌 것

**결정**:
- 문서 포맷 강제 안 함
- 인덱스는 물리적 다중 뷰가 아니라 구조화 필드 + 런타임 필터
- DB는 원본이 아니라 파생 검색 인덱스(SQLite FTS5 우선 검토)

**미결 — 다음 세션에서 구체화**:
1. 인덱스 스키마 최종 설계 — WP/DWP(또는 신규 "검토 문서" 유형)의 메타 필드를 뭘로 정할지,
   태그 체계, 필수/선택 필드 구분.
2. WP/DWP 자체의 "포맷 완화 + 메타 강화"를 어디까지 밀고 갈지 — 전면 개편 vs 신규 문서
   유형에만 우선 적용.
3. SQLite FTS5 인덱스를 언제/어떻게 재생성할지 — CLI 훅 / 파일 변경 감지 / 수동 명령.
4. 기존 LOADSTAR CLI(도구) 쪽에 이 기능을 어떻게 편입시킬지 — 툴 저장소 쪽 별도 작업 필요
   (이 문서는 SPEC/설계 논의 범위까지만).
5. "다양한 뷰"(시간순/카테고리별) UI 형태 — 프로토타입(예: 정적 페이지)으로 먼저 시험해볼지.
