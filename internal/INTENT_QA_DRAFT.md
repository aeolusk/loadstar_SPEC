## 1. 배경 — 맥락 전달의 본질적 비용

### 1.1 관찰

- 최초 구현 시 상세한 명세 전달이 가장 효율적이지만, 현실 개발은 대부분 그렇게 진행되지 않는다.
- 수정 단계에서는 "X가 안 돼, 고쳐줘"보다 "현재 동작 / 원하는 동작 / 이유"를 다시 기술하는 편이 결과 품질이 높다.
- 즉 **수정의 본질은 맥락(의도)의 재전달**이며, 이는 사용자에게 적지 않은 사고 비용을 요구한다.

### 1.2 LOADSTAR의 한계

WayPoint는 WHAT/HOW의 영속화에는 강하나, **의도(WHY/WHY-NOT/MUST/TRADE-OFF)** 의 영속화는 사용자의 자발적 기술에 의존한다. 작업 중간에 맥락을 능동적으로 기술하는 것은 본 작업보다 추상도가 높은 통합 사고를 요하기 때문에, "적당한 비용으로 가능"하지 않다는 것이 현 시점 판단이다.

### 1.3 자동 추출의 한계

코드/diff 기반 자동 요약은 "무엇을 했는가"는 잡지만, **사용자 머릿속에만 있던 의도**(왜 X 대신 Y, 어떤 케이스를 의도적으로 제외, 어떤 제약 때문에 이 모양인가)는 캐낼 수 없다. 결국 git log를 보강하는 정도에 머문다.

## 2. 핵심 아이디어 — 결과물 시점의 Q&A

> 일정 부분 결과물이 생성되었을 때, 그 결과물을 기반으로 AI가 의도를 다시 점검한다. 자동 추출이 아니라 **Q&A 형태의 양방향 정리**.

### 2.1 왜 Q&A인가

- 사용자의 일방적 기술은 비용이 크다 (통합 사고 요구).
- AI의 일방적 추출은 표면적이다 (머릿속 의도 못 잡음).
- **양방향 Q&A는 비용을 분산**한다: AI가 결과물을 보고 가설을 세워 묻고, 사용자는 그 가설을 yes/no + 보충으로 답한다. 답변 과정에서 사용자 자신의 의도도 명확해지는 부수 효과.

### 2.2 "검문"이 아니라 "정리" 톤

질문 형태가 결정적이다.

- ❌ "왜 이렇게 했어요?" → 백지 회상, 비용 큼
- ✅ "제가 이해한 바로는 X 의도이고 Y 케이스는 의도적으로 제외하신 것 같습니다. 맞나요?" → 가설 검증, 비용 낮음

사용자는 틀린 부분만 짚으면 된다. AI의 1차 가설이 곧 80% 초안 역할을 한다.

### 2.3 트리거 시점

- **WP STATUS 전환 직전** (S_PRG → S_STB) — 자연스러운 게이트
- **팀 회의 주기** — 개발방법론 차원에서 정례 검토
- 너무 잦으면 흐름 단절, 너무 뜸하면 의도 휘발 — 위 두 트리거가 균형점

## 3. 요소별 프롬프트 카탈로그

### 3.1 의도의 "모양"은 layer별로 다름

| 요소 | 의도의 전형적 형태 | 질문 패턴 예시 |
|:---|:---|:---|
| **DB** | 정규화/비정규화 트레이드오프, 인덱스/제약 결정 | "이 테이블을 분리한 이유가 X인가? Y 케이스를 막기 위함인가?" |
| **REST** | verb 선택, 멱등성/에러 의미, 계약 경계 | "이 엔드포인트를 PUT 대신 POST로 한 건 멱등성 보장 어려운 케이스 때문인가?" |
| **UI** | 사용자 흐름 가정, 의도적 제외 상태, 어포던스 | "이 화면에서 빈 상태를 따로 처리 안 한 건 데이터가 항상 존재한다는 가정인가?" |
| **도메인 로직** | 비즈니스 규칙, 거절된 대안 | "이 검증 순서가 의미 있는 건가, 우연인가?" |

공용 프롬프트 하나로 커버하려는 시도는 보통 실패한다. 요소별 전용 프롬프트 세트가 필요.

### 3.2 우선순위가 높은 결정 패턴

수정 단계에서 가장 자주 재소환되는 결정 형태:

1. **선택 결정** — 왜 X 대신 Y를 골랐나 → 나중에 X로 갈아탈 때 필요
2. **제외 결정** — 어떤 케이스를 의도적으로 뺐나 → 빠진 케이스 만났을 때 필요
3. **제약 결정** — 어떤 외부 제약 때문에 이 모양인가 → 제약이 풀렸을 때 필요

프롬프트는 위 세 패턴을 조준하면 같은 비용으로 더 가치 있는 데이터가 나온다.

### 3.3 시작 범위

처음부터 모든 요소를 커버하려 하면 못 시작한다. **DB / REST 부터** 시작 권장 — 결정 포인트가 비교적 명확. UI는 의도가 흐물흐물해서 후순위.

## 4. 프롬프트 + 결과 저장

### 4.1 저장 단위

WP 전체를 한 덩어리로 묶지 않는다. **Q&A 한 쌍 단위 + 요소 태그**로 쪼개야 검색 정확도가 나온다.

### 4.2 스키마 (안)

```yaml
- intent_qa_id: <unique>
  wp_address: W://root/api/payment
  element_type: db | rest | ui | domain
  prompt_id: <카탈로그 참조>
  prompt_version: <버전>
  question: <AI가 던진 가설형 질문>
  answer: <사용자 응답>
  decision_pattern: choice | exclusion | constraint
  created_at: <date>
```

- **`prompt_version` 필수**: 프롬프트는 코드처럼 버전 관리 대상. 같은 질문이 시간에 따라 바뀌면 과거 답변과 비교 기준이 사라진다.
- **검색 키**: `wp_address` + `element_type` + 키워드. RAG 연동 전이라도 단순 매칭으로 시작 가능.

### 4.3 staleness 정책 — 별도 처리 안 함

코드가 변해서 과거 Q&A가 무효가 되더라도 별도 invalidation 시스템을 두지 않는다.

- 수정 중 개발자가 무관한 결과를 보면 무시할 것 — 그 자체가 자연 도태.
- 별도 정합성 체크는 비용 대비 가치가 불분명.
- 후속 설문에서 "misleading했던 항목" 정도만 잡으면 충분.

## 5. 평가 — 자연 사용 + 후속 설문

### 5.1 평가 원칙

데이터의 가치 척도는 **"수정 작업에 실제로 도움이 되었는가"** 단 하나. 추상적인 "의도 충실도" 같은 측정 불가능한 목표는 두지 않는다.

### 5.2 측정 방법

- **개발 단계의 자연 사용**: 수정 작업 중 개발자(또는 AI)가 과거 Q&A를 참조했는지, 도움이 되었는지를 가벼운 라벨링(👍/👎)으로 수집.
- **프로젝트 종료 시 설문**: 어떤 항목이 유용했는가, misleading했는가, 누락이 컸던 영역은 어디인가.

### 5.3 자연 사용을 위한 전제

자연 사용이 일어나려면 **개발자가 이 데이터의 존재를 잊지 않아야** 한다. 수정 중인 파일/WP에 연결된 Q&A가 자동으로 가시화되는 UI 통합이 필요 (8장 참조).

## 8. UI 통합 — RAG 연동 시점에 함께

`loadstar_ui`에서 본 데이터를 노출하는 작업은 **RAG 기능 연동 후 프로젝트 검토와 함께** 구현한다.

예상 노출 형태 (예비 스케치):

- 수정 중인 파일/WP에 연결된 Q&A를 사이드패널에 자동 표시
- 요소 타입 필터 (DB만, REST만 등)
- 👍/👎 라벨링 인터페이스
- RAG 검색을 통한 유사 결정 패턴 탐색

WP 주소 기반 단순 매칭으로도 1차 노출은 가능하지만, 본격 가치는 RAG 연동 이후.
