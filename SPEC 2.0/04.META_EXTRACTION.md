# 📊 LOADSTAR 2.0 — Meta Extraction & Index

md 파일(원본)에서 **문서 자체에 대한 메타 정보**를 추출해 SQLite에 적재하고, 이를 근거로 다양한 관점의 조회를 지원하는 구조를 정의한다. **프로젝트 진행 상태(작업 내용)는 이 DB가 다루는 대상이 아니다** — 그건 md 본문에 있고, 필요할 때 별도 프로그램이 그 자리에서 읽는다.

---

## 1. 목적

md 파일은 다양한 프로젝트 정보를 담고 있으며, 이를 시간순 / 기능별 / 데이터 기준 / 키워드 기반 등 여러 관점으로 조회할 수 있어야 한다. 이를 위해 md 파일의 **문서로서의 정체성**(타입, 요약, 키워드, 생성·수정 시각, 이력, 관계)을 추출해 DB에 담는다.

**DB가 담지 않는 것**: STATUS, TODO 진행률, ISSUE 내용처럼 "이 작업이 지금 어떤 상태인가"에 해당하는 내용. 이런 값은 WP/DWP라는 특정 포맷의 도메인 어휘이지, 문서 일반에 대한 메타가 아니다. 캐싱하면 원본이 바뀔 때마다 다시 동기화해야 하는 부담만 생기고, 이 규모에서는 그때그때 파일을 읽어 계산하는 비용이 낮다.

## 2. 파이프라인 구성

```
md 파일 (원본)
    ↓
① 구조 추출기 (결정론적) ──→ nodes / edges / history
    ↓                              ↑
② AI 보강 단계 (생성) ────────→ ai_facets (키워드, 다각도 요약)
                                    │
                          SQLite (①②만 적재, 항상 최신일 필요 없음)
                                    │
                    ┌───────────────┴───────────────┐
                    │                                │
              Viewer가 직접 조회                ③ 온디맨드 도메인 조회기
        (날짜/타입/키워드/관계 기반 브라우징)   (STATUS/TODO/ISSUE 등,
                                                호출 시점에 md를 직접 읽어 계산)
```

- **① 구조 추출기**: md의 문서 정체성(파일명 필드 + IDENTITY.SUMMARY + CONNECTIONS)과, 포맷에 상관없이 마크다운 문법만으로 뽑을 수 있는 구조적 사실(제목 대체값·목차·체크박스 개수 등)을 결정론적으로 파싱. 항상 실행, 저비용.
- **② AI 보강 단계**: LLM이 문서를 보고 키워드·다각도 요약을 생성. 비결정적이고 비용이 있어 ①과 별도 주기로 실행될 수 있다.
- **③ 온디맨드 도메인 조회기**: STATUS/TODO/ISSUE/ATTACHMENTS/TABLES 등 WP·DWP 고유 슬롯을 다룬다. DB에 캐싱하지 않고, 조회 시점에 대상 md 파일(들)을 직접 읽어 계산한다. "이슈 있는 문서만 보기" 같은 뷰도 nodes에서 대상 file_path 목록을 뽑은 뒤 이 조회기로 일괄 스캔해서 만든다 — DB에 issue 상태를 미리 저장해두지 않는다.
- **TODO 롤업** (§8): 별도 파이프라인 단계가 아니라 ③의 결과를 UI가 보여주고, 사용자 상호작용은 곧바로 WP md에 되쓰는 방식 — 중간 파일이나 별도 포맷은 두지 않는다. 상세는 UI 설계 시점에 다룬다.

## 3. 저장소 선택 — 순수 RDBMS, FTS5·벡터 미사용

- 자유텍스트 검색은 사용하지 않는다. grep으로 충분한 규모다.
- 키워드/요약은 ②(AI 보강)가 생성한 **문자열**을 저장하는 것으로 시작한다. 임베딩·유사도 검색(RAG)은 지금 범위에 넣지 않는다 — 필요성이 확인되면 별도로 검토한다.
- SQLite는 md에서 추출한 문서 메타(①②만)의 파생 캐시다. 언제든 재생성 가능해야 한다.

## 4. ① 구조 추출기

- **역할**: 파일명(FORMAT/VER/DATE/이름) + IDENTITY.SUMMARY + CONNECTIONS를 파싱해 nodes/edges에 적재.
- **공통 레이어만 다룬다**: WP/DWP를 구분하지 않고 모든 FORMAT에 동일하게 적용되는 필드만 뽑는다. 새 FORMAT이 추가돼도 이 추출기는 바뀌지 않는다.
- **구조적 사실의 기준**: "이 문법 요소가 무엇을 의미하는지 LOADSTAR 도메인 지식 없이도 뽑을 수 있는가"가 기준이다. 예: 체크박스(`- [ ]`/`- [x]`) 개수는 마크다운 문법 차원의 사실이라 포함하지만, 그 체크박스가 STATUS 상 무엇을 뜻하는지 판단하는 건 여전히 §7(온디맨드 도메인 조회기)의 몫이다.
- **history**: Git 커밋 로그를 파싱해 구조화한 파생 테이블. 변경 시각·커밋 해시·커밋 메시지 원문만 담는다 — 프로젝트 내용을 해석·가공하지 않는다. 별도로 write되는 로그가 아니라 git log를 읽어 채우는 미러다 — git이 여전히 유일한 원본이다.
- **트리거**: 파일 변경 감지 vs 주기 실행 — 추후 결정 (§7과 동일 미결 사항).

## 5. ② AI 보강 단계

- **역할**: 문서(SUMMARY, GOAL 등)를 LLM에 보여 키워드와 여러 각도의 요약을 생성.
- **범위(현재)**: 문자열 생성까지만. 임베딩·벡터 저장소는 도입하지 않는다.
- **다각도 요약**: 고정된 몇 개 필드가 아니라 `facet_type`이 자유로운 key-value 구조로 저장한다 — 요약 축이 늘어나도 스키마 변경이 필요 없다.
- ①과 분리된 이유: LLM 호출은 비용·지연이 있고 결과가 비결정적이라, 파일이 바뀔 때마다 매번 재실행하기보다 별도 주기/트리거로 운용하는 편이 합리적이다(구체 주기는 미정).

## 6. DB 스키마

### 6.1 nodes — 문서 정체성 (① 구조 추출기가 채움)

| 필드 | 출처 | 비고 |
|:--|:--|:--|
| `id` | — | PK |
| `format` | 파일명 `[FORMAT]` | |
| `ver` | 파일명 `[VER]` | |
| `name` | 파일명 `이름` | |
| `created_date` | 파일명 `생성일` | |
| `modified_at` | git 마지막 커밋 시각 | history와 동일 소스에서 파생 |
| `file_path` | 물리 경로 | |
| `title` | IDENTITY.SUMMARY (있으면) 또는 문서의 첫 헤딩/첫 줄 (없으면) | 한 줄 라벨. 봉투 없는 자유 형식 md도 커버 |
| `toc` | 문서의 헤딩 구조 (H1/H2/...) | JSON (레벨+텍스트 리스트) |
| `checklist_total` / `checklist_done` | 문서 내 체크박스(`- [ ]`/`- [x]`) 개수 | 마크다운 문법 차원의 사실. 의미 해석은 §7 담당 |

### 6.2 edges — 문서 간 관계 (① 구조 추출기가 채움)

```
edges(from_id, to_id, edge_type)
```

- `edge_type`: `PARENT` \| `REFERENCE` \| `GROUP_ITEM`
- `PARENT`/`REFERENCE`는 WP/DWP가 스스로 선언한 관계. `GROUP_ITEM`은 GROUP의 `ITEMS`에서 파생 — 방향은 GROUP→멤버(WP/DWP/하위 GROUP)이며, 멤버 쪽은 자신이 속한 GROUP을 전혀 모른다(`appendix/GROUP.md`).
- 관계는 "문서가 문서를 가리킨다"는 구조적 사실이라 제네릭 레이어에 남긴다 — 기능별 그룹(GROUP_ITEM 재귀 — 하위 GROUP까지 타고 들어가며 수집), 데이터 기준 뷰(REFERENCE 역방향)의 근거.
- `CHILDREN`은 저장하지 않고 `PARENT`의 역방향 조회로 대체(§9 Validator에서 교차검증에 사용).

### 6.3 history — Git 파생 이력 (① 구조 추출기가 채움)

```
history(id, node_id, changed_at, commit_hash, message)
```

- `message`: git 커밋 메시지 원문. 해석·가공 없이 그대로 저장.
- git log를 파싱해 채우는 파생 테이블. 재생성 가능.
- 파일 리네이밍이 섞인 경우 커밋 이력 추적이 매끄럽지 않을 수 있음 — 알려진 한계로 남겨두고 필요 시 별도 검토.

### 6.4 ai_facets — AI 보강 결과 (② AI 보강 단계가 채움)

```
ai_facets(node_id, facet_type, value, generated_at)
```

- `facet_type` 예: `keyword`, `summary:scope`, `summary:issue` 등 — 자유롭게 확장.
- 문자열만 저장. 벡터 없음.

## 7. ③ 온디맨드 도메인 조회기 (DB 미저장)

WP/DWP 부록(`appendix/WP.md`, `appendix/DWP.md`)에 정의된 고유 슬롯을 다룬다. DB 테이블이 아니라 **조회 시점에 실행되는 프로그램**이다.

| 대상 | 슬롯 |
|:--|:--|
| WP | STATUS, GOAL 존재 여부, TODO 총/완료 개수, RECURRING 개수, ISSUE 내용, ATTACHMENTS |
| DWP | TABLES 구조, ATTACHMENTS |

- nodes에서 대상 file_path 목록(예: format=WP 전체)을 뽑은 뒤, 이 조회기로 일괄 스캔해 뷰를 구성한다.
- "구현 완료/진행중/이슈 있는" 같은 상태 기반 뷰는 이 조회기 결과를 그때그때 계산해서 만든다 — DB에 상태를 미리 넣어두지 않는다.

## 8. TODO 롤업 — 방향만 확정, 상세 설계는 UI 설계 시점으로 보류

여러 WP에 흩어진 TODO를 한눈에 조망·편집하고 싶다는 요구는 있으나, 별도 md 포맷(예: `[TODO]...`)은 만들지 않기로 했다. 대신:

- **DB/실시간 조회는 읽기(표시) 전용**이다 — TODO 상태의 진짜 저장소는 여전히 WP md 파일뿐이다(§1 원칙 유지).
- 화면에는 온디맨드 도메인 조회기(③)로 여러 WP의 TODO를 매번 새로 뽑아 보여준다. 사용자가 상호작용하면(체크박스 토글 등) **그 즉시 해당 WP md 파일에 직접 기록**한다 — 중간에 별도로 저장·동기화해야 하는 파일이 없다.
- GROUP(선택)의 `ITEMS`를 활용하면 "이 GROUP 산하 TODO만 보기" 같은 스코프 좁히기가 가능하다.
- 상세 UI/상호작용 설계는 추후 UI 설계 단계에서 다룬다.

## 9. Validator (검토 중)

- CONNECTIONS가 가리키는 파일명이 실제 존재하는가 (dangling reference)
- WP의 PARENT ↔ 상위 요소의 CHILDREN 선언이 서로 일치하는가
- 동일 FORMAT 폴더 내 파일명 충돌

추출기(①)에 결합할지 독립 실행할지는 미정.

## 10. 미결 사항

1. ① 구조 추출기의 트리거 방식 (파일 변경 감지 / 주기 실행 / git hook)
2. ② AI 보강 단계의 실행 주기 — ①과 다른 트리거가 필요할 가능성
3. Validator를 추출기에 결합할지 분리할지
4. RAG(임베딩 기반 유사도 검색) 필요성 — 지금은 범위 밖, 필요성이 확인되면 별도 검토
5. history 테이블의 파일 리네이밍 추적 방식
6. TODO 롤업 UI의 상세 상호작용 설계 (§8) — UI 설계 단계로 이관
